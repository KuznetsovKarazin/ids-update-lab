# Оставшиеся аппаратные эксперименты: комплект 020

Комплект меняет прошивку и формат хранения. Текущие результаты 018–019 остаются отдельными доказательствами старого бинарного файла. После установки 020 на MCU будет заводская модель A версии 1. Это намеренное лабораторное перепровизионирование с удалением истории версий, а не разрешённый механизм отката для атакующего.

Сначала сохраните существующие `runs` и образ flash согласно общему README. Для работы используются ESP32-S3 и прежний USB COM13. FNB58 может оставаться физически в цепи, но эти сценарии не измеряют энергию. Для COM13 должна быть закрыта другая программа терминала. Служебный USB-порт FNB58 не используется вместо порта MCU.

Все команды запускаются из `E:\ids-update-lab`. Архив распаковывается рядом со старым проектом в новую папку `completion020`. Прошивки, исходники, подписанные пакеты, эталонные ответы и скрипты входят в комплект. Подписи проверяются до обращения к плате; приватного ключа в комплекте нет. Повторное обучение не требуется.

## Шаг 1. Проверка файлов без платы

```powershell
Set-Location E:\ids-update-lab
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py inspect --model lr --policy bundle
```

Требуется `status: complete`, `hardware_access_attempted: false`. Иначе не прошивайте плату: пришлите полный текст ошибки.

## Шаг 2. Установка исправленного хранения и функциональная проверка LR

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py flash --model lr --policy bundle --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-bundle-flash
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py smoke --model lr --policy bundle --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-bundle-smoke
```

`flash` проверяет MAC через ROM до записи, устанавливает заранее собранную прошивку, очищает только выделенные модельные разделы и журнал, проверяет A. Команды eFuse отсутствуют. `smoke` повторно создаёт заводское состояние A, проверяет все 258 входов на A, устанавливает B и проверяет те же 258 входов, затем C (точные параметры B, новая версия), снова 258 входов. После перезапуска проверяется один контрольный вход. Ожидается 775 вычислений и 0 несовпадений меток. Плата остаётся на C версии 3.

При любом непредусмотренном сбое сценарий останавливается. Не повторяйте команду с тем же каталогом и не переименовывайте неудачный запуск в успешный. Сохраните `summary.json`, `transcript.jsonl` и подкаталоги. Скрипт не продолжает незавершённый опыт автоматически.

## Полная автоматическая серия — рекомендуемый путь после успешного smoke

Вместо последовательного выполнения всех команд ниже можно запустить один управляющий сценарий:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py series --model all --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-full-series
```

Он заранее сохраняет весь план, выполняет smoke, прерывания для bundle, отрицательные контроли для всех пяти конфигураций и 30 блоков измерения затрат. В каждом блоке представлены LR bundle, LR compatible, LR whole, DT bundle и DT whole. Порядок конфигураций циклически меняется, чтобы каждая одинаковое число раз оказывалась первой, второй и т. д. Перед каждой сменой конфигурации прошивка и заводское состояние восстанавливаются автоматически. Вмешательство пользователя между испытаниями не нужно.

Для одной только окончательной серии затрат после уже выполненных функциональных проверок используется:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py costs-suite --model all --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-balanced-costs
```

`--model lr` или `--model dt` ограничивает серию соответствующей моделью. План сохраняется в `campaign_manifest.json`, а явное сопоставление блоков, конфигураций и путей — в `cost_suite_manifest.json`. Парные сравнения затрат следует строить по этой общей серии, а не объявлять независимые одиночные запуски парными задним числом. Полная серия включает 60 полных OTA-передач на каждую модель, поэтому занимает существенно больше времени, чем smoke; планируйте непрерывное питание ПК и платы.

Остальные команды ниже нужны для поэтапного запуска и диагностики. Если полная автоматическая серия завершилась успешно, дублировать её всеми отдельными командами не требуется.

## Шаг 3. Программные прерывания LR

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py faults --model lr --policy bundle --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-bundle-faults
```

120 испытаний: шесть точек × два исходных состояния целевого слота × десять повторов. Порядок зафиксирован генератором с seed 24092026 до первой операции с платой. Перед каждым испытанием скрипт проверяет ROM MAC, сбрасывает модельные разделы и журнал, даёт прошивке установить A. Для состояния `reused` предварительно устанавливается B, а прерывается установка C поверх старого слота A.

| Точка перезапуска | Должно восстановиться |
|---|---|
| `after_erase` | прежняя активная версия |
| `after_write` | прежняя активная версия |
| `after_verify` | прежняя активная версия |
| `after_slot_commit` | прежняя активная версия |
| `after_journal_body` | прежняя активная версия |
| `after_commit` | новая версия |

После восстановления проверяются восемь фиксированных эталонных входов, отклонение подписанного старого выпуска A и ещё один вход. Ожидается 120 проверенных восстановлений и 1080 вычислений. Нулевая доля неудач характеризует только эти программные точки на данном экземпляре платы. Случайное физическое отключение питания и прерывание внутри операции flash здесь не измеряются.

## Шаг 4. Отрицательные контроли и затраты LR bundle

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py negatives --model lr --policy bundle --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-bundle-negatives
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py costs --model lr --policy bundle --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-bundle-costs
```

Отрицательные контроли: 10 неверных подписей, 10 правильно подписанных пакетов с чужим контрактом признаков, 10 повторов версии. Каждый начинается с A. После отклонения проверяются восемь входов, перезапуск и один вход; всего 30 отклонений и 270 вычислений.

Затраты: 30 отдельных повторов с восстановлением заводского состояния на одной плате, в каждом A→B на чистом втором слоте и B→C на ранее занятом первом слоте. На каждой версии проверяются первые 16 заранее зафиксированных входов; после перезапуска C — один вход. Ожидается 60 принятых обновлений и 1470 вычислений. Сценарий сохраняет все времена MCU по стадиям, размеры пакетов, байты протокола, ответы платы и времена хоста. Очистка и восстановление через esptool не включаются в стоимость операции обновления.

## Шаг 5. Корректная альтернатива с неизменяемой предобработкой LR

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py inspect --model lr --policy compatible
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py flash --model lr --policy compatible --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-compatible-flash
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py smoke --model lr --policy compatible --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-compatible-smoke
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py negatives --model lr --policy compatible --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-compatible-negatives
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py costs --model lr --policy compatible --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-compatible-costs
```

В этом варианте прошивка действительно использует заводские нормализацию и порог A. Коэффициенты B заранее преобразованы для сохранения решения при таком ограничении. Сохраняется решение классификации в точной арифметике; вероятности могут измениться. Для количественной проверки MCU используется собственный эталон этого экспортированного пакета. Формат по-прежнему содержит все поля конвейера, поэтому этот baseline не означает передачу файла только с весами и не обеспечивает отдельного выигрыша в байтах.

## Шаг 6. Полная OTA-прошивка LR

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py inspect --model lr --policy whole
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py flash --model lr --policy whole --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-whole-flash
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py smoke --model lr --policy whole --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-whole-smoke
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py negatives --model lr --policy whole --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-whole-negatives
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py costs --model lr --policy whole --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-whole-costs
```

Перед каждым испытанием whole-firmware перепрошивается A, начальные OTA-данные, очищается неактивный OTA-раздел и модельные разделы с журналом. Это обеспечивает воспроизводимое состояние после ранее установленной C. За одну серию costs выполняются 60 OTA-передач: на B и на C. После `FW_END` скрипт отдельно проверяет, что пока работает прежняя версия, затем перезапускает MCU и проверяет новую сборку и параметры.

Отрицательные контроли для whole отличаются от компонентных: 10 неверных подписей метаданных, 10 повторов подписанных метаданных версии A, 10 образов с повреждённым последним байтом при правильных подписанных метаданных B. Последний случай должен отклоняться при `FW_END` с `image_sha256`; он выполняется в отдельной серии и не загрязняет исходное состояние измерений затрат.

Для сопоставления приводим отдельно время работы MCU, время передачи по используемому протоколу и задержку перезапуска. Протокол использует hex и stop-and-wait с фрагментом 256 байт; время хоста не является общим свойством технологии OTA. Байты стирания и записи — расчёт по исходным вызовам API, а не измеренный ресурс flash.

## Шаг 7. Вторая модель — дерево DT5

Повторяются bundle и whole; режима compatible для дерева в этом комплекте нет.

```powershell
$py = '.\.venv\Scripts\python.exe'
$runner = '.\completion020\tools\run_completion.py'
foreach ($policy in @('bundle', 'whole')) {
    & $py $runner inspect --model dt --policy $policy
    if ($LASTEXITCODE -ne 0) { throw "inspect dt/$policy failed" }
    $commands = if ($policy -eq 'bundle') { @('flash','smoke','faults','negatives','costs') } else { @('flash','smoke','negatives','costs') }
    foreach ($command in $commands) {
        & $py $runner $command --model dt --policy $policy --port COM13 --board-id esp32s3-a0f262ebb558 --output "runs\020-dt-$policy-$command"
        if ($LASTEXITCODE -ne 0) { throw "Stopped at dt/$policy/$command; preserve logs" }
    }
}
```

DT5 использует те же восемь сырых признаков, собственный подписанный контракт ABI3 и уже обученные деревья A/B. Никакого подбора модели по новым аппаратным результатам скрипт не выполняет.

## Что прислать

Каждый каталог содержит неизменяемый план `campaign_manifest.json`, исходный preflight, журналы esptool, вложенные trial-каталоги с сырыми RX/TX, проверками вычислений и `summary.json`. Сохраняйте неудачные испытания наравне с успешными. Соберите их штатным инструментом общего архива из README; нельзя исключать неудачные попытки из анализа.

Эти серии закрывают перенос LR/DT на MCU, повторные программные прерывания, отрицательные контроли и сравнение реализации способов обновления. Они не дают независимого качества обнаружения на новых данных, физической надёжности при пропадании питания, delta OTA или откалиброванной энергии. Для этих задач предусмотрены отдельные протоколы.

## Явное восстановление после незавершённой прошивки

Если прежний запуск оборвался во время перепровизионирования и `STATUS` уже не сообщает готовую известную прошивку, обычный `flash` намеренно останавливается. Сначала сохраните неудачный каталог. Затем можно явно выбрать ROM-восстановление:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py flash --rom-recovery --model lr --policy bundle --port COM13 --board-id esp32s3-a0f262ebb558 --output runs\020-lr-recovery
```

Оно пропускает проверку работающего приложения, но по-прежнему обязательно проверяет ESP32-S3 и MAC через ROM до первой записи, затем устанавливает выбранную заводскую прошивку и очищает экспериментальные разделы. Это отдельное восстановление с собственным журналом, а не продолжение прерванного испытания. После него нужен новый smoke и разбор исходной ошибки до запуска большой серии.

Для дополнительного измерения энергии полной OTA отдельный повтор `costs --model lr --policy whole` может использовать `--energy-baseline-seconds 10`. Тогда перед каждым принятым обновлением записывается десятисекундное окно без команд. Этот дополнительный прогон не смешивается с основной серией затрат. Времена окон сохранены в `events.jsonl`; они не заменяют синхронизацию с записью FNB58 и проверку единиц измерения.
