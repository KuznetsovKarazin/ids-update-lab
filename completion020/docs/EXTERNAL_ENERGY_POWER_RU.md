# Дополнительные эксперименты: независимые данные, энергия, отключение питания

Эти три ветви имеют разные условия запуска. Код оценки и интегрирования готов,
но **новый независимый датасет пока не предоставлен**, FNB58 не откалиброван,
а для физического отключения питания **нужен внешний силовой ключ**.
Наличие Pico 2 само по себе не позволяет безопасно коммутировать питание ESP32.

## 1. Новый внешний набор данных — оценка замороженных моделей на ПК

Здесь не требуется плата. Модели и пороги не переобучаются. Оцениваются все восемь
вариантов LR из 019 и два уже обученных дерева DT5. Порог для каждого взят из
подписанного пакета. Результаты на новых данных нельзя затем использовать для
подбора порога и продолжать называть результат независимым тестом.

Требуется CSV с восемью **сырыми** признаками и меткой `label`:

| Столбец | Единица |
|---|---|
| duration | секунды |
| src_bytes, dst_bytes, missed_bytes | байты |
| src_pkts, dst_pkts | число пакетов |
| src_ip_bytes, dst_ip_bytes | байты |
| label | `0` — нормальный поток, `1` — атака |

Нужны те же определения направления потока, длительности и счётчиков. Одинаковые
названия столбцов другого датасета не доказывают совпадения смысла признаков.
Нельзя подставлять нули вместо отсутствующих признаков, переводить метки по
догадке или повторно подавать уже нормализованные/log1p-признаки.

1. Сначала зафиксируйте происхождение данных: источник, файл, сеанс сбора,
   временной диапазон, способ получения восьми признаков и разметки. Лучше
   отдельный ранее не использованный сеанс TON_IoT с тем же извлечением признаков.
2. Положите CSV, например, `E:\ids-update-lab\external\new_session.csv`.
3. Скопируйте `completion020\docs\external_provenance_TEMPLATE.json` в
   `external\provenance.json`. Заполните фактические значения вместо `FILL`.
   Поля со значением `null` заменяйте только после проверки. Независимость
   происхождения подтверждает исследователь; программа не может установить её
   по одному CSV. SHA-256 получите так:

```powershell
Get-FileHash .\external\new_session.csv -Algorithm SHA256
```

4. Запустите один раз, сохраняя все варианты и любые отрицательные результаты:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\evaluate_external.py evaluate --csv .\external\new_session.csv --provenance .\external\provenance.json --output .\runs\external-020
```

В комплект включены SHA-256 отпечатки всех 211 043 ранее доступных строк по восьми
float32-признакам (92 330 уникальных вектора). Они рассчитаны без прогнозов и
чтения меток старого теста. Точные совпадения с любым прежним вектором автоматически
исключаются **по заранее заданному правилу**, число и индексы исключённых строк
сохраняются. Прежний исходный CSV целиком отклоняется. Это не создаёт независимость
по сеансам, устройствам или времени: соответствующее ограничение останется в отчёте.

Отчёт содержит recall, FPR, balanced accuracy, изменения решений относительно
LR_B, 2000 парных кластерных bootstrap-повторов с seed 24092026. Если в CSV есть заранее определённый идентификатор независимого сеанса/устройства,
укажите его в `bootstrap_group_column` и объясните группировку в
`bootstrap_group_description` **до запуска**. Тогда кластер — вся эта группа.
Иначе используется явно обозначенная описательная группировка по одинаковому
float32-вектору; её интервалы не учитывают зависимость разных векторов одного
устройства/сеанса/временного окна. Программа не выбирает группировку по метрикам. Если bootstrap создаёт выборки без
одного класса, программа сообщает их число и не выводит интервалы вместо
незаметного повторного отбора. Отчёт и исходный CSV нужно сохранить вместе.

До получения подходящего нового набора эта ветвь имеет статус «ожидает данные».
Не делайте новый случайный train/test split старого файла для имитации нового теста.

## 2. FNB58 — сначала корректная запись, затем интегрирование

Объект измерения — мощность на выбранной границе питания платы через USB,
включая регулятор, светодиоды и интерфейс. Это не энергия одного ядра ESP32.
Используйте одну и ту же схему кабелей, напряжение 5 V, настройки платы и состояния
USB во всех вариантах. Не включайте режимы повышения напряжения/зарядных триггеров.

В ПО FNB58 запишите VBUS, IBUS, PBUS, NRG и, по возможности, CAP. Сохраняйте исходный
CFN. Оставьте до и после серии участки покоя. Настройка 100 sps означает частоту
сохранённых строк; множество одинаковых соседних значений не подтверждает 100
независимых измерений в секунду. Не выделяйте одну операцию длительностью 35–42 мс
по одному пику. Для коротких обновлений нужны заранее заданные длинные блоки,
серия блоков и одинаковые интервалы ожидания. Разные версии для серии должны быть
подписаны заранее: повтор одной версии будет отклонён и измерит другую операцию.

Для серий, выполненных основным скриптом, границы блоков берутся из сырых временных
меток хоста. В CFN абсолютных UTC-меток нет, поэтому требуется независимая оценка
смещения шкал времени. Зафиксируйте интервал неопределённости по наблюдаемому
старту записи/видеозаписи/контрольному маркеру. Нельзя совмещать кривые произвольным
сдвигом до получения ожидаемой энергии. При ручном запуске широкий интервал лучше
ложной миллисекундной точности. Смещение определяется как
`время_CFN = относительное_время_хоста + offset`.

Для вторичной записи **полной прошивки** предусмотрен конкретный сценарий. Это
отдельный повтор, его не объединяем с основной серией времени без пауз. Сначала
основные программные проверки должны быть завершены. Подготовьте LR whole:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py flash --model lr --policy whole --port COM13 --board-id esp32s3-a0f262ebb558 --output .\runs\energy-whole-020-flash
```

Затем в FNB58 начните **новую** запись и сохраните наблюдаемый интервал запуска
в привязке к UTC хоста (например, отметки PowerShell до и после нажатия «запись»,
с запасом на задержку приложения). Зафиксируйте, какое относительное время CFN
соответствует этому событию. Не считайте относительный ноль CFN моментом открытия
COM или запуска опыта без проверки. После этого:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\run_completion.py costs --model lr --policy whole --port COM13 --board-id esp32s3-a0f262ebb558 --energy-baseline-seconds 10 --output .\runs\energy-whole-020
```

Серия содержит 30 повторов A→B→C. Перед каждым обновлением записывается отдельный
10-секундный участок покоя. Все восстановления заводского состояния, стирания
при подготовке и служебные проверки находятся **вне** окон энергии обновления.
Запись FNB58 идёт непрерывно; после завершения сохраните CFN отдельно.
Полная прошивка включает передачу, выбор образа, перезагрузку и подтверждение STATUS.
Таким образом измеряется энергия всей операции используемого протокола.

Из сырых журналов получите неизменяемые границы операций и их собственные фоны:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\generate_energy_windows.py --run .\runs\energy-whole-020 --output .\runs\energy-whole-020-windows.json
```

В созданном файле заполните **только** диапазон
`cfn_time_minus_host_relative_time_s` и поля обоснования синхронизации. Поля окон
связаны контрольным хешем с журналами; анализатор отклонит их случайную правку.
`host_origin_utc_ns` — UTC, соответствующий нулю относительной шкалы хоста.
Если наблюдение установило, что ноль CFN возник между UTC `L` и `U`, то диапазон
смещения равен `[(host_origin_utc_ns-U)/1e9, (host_origin_utc_ns-L)/1e9]`.
Значения L/U также выражаются в наносекундах. При ненулевом времени CFN у события
это время добавляется к обеим границам. Такой расчёт не устраняет дрейф часов
и задержку внутреннего тракта FNB58; они должны войти в обоснованный запас.

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\energy_analysis.py --cfn .\runs\energy-whole-020.cfn --windows .\runs\energy-whole-020-windows.json --output .\runs\energy-whole-020-analysis
```

Для произвольной ранее выполненной записи без таких событий возможен ручной
вариант ниже, с явно записанным происхождением границ. Он не заменяет аккуратную
новую запись.

1. Скопируйте `energy_windows_TEMPLATE.json` в папку конкретного опыта.
2. Замените **все демонстрационные интервалы** фактическими интервалами покоя и
   операции, задайте диапазон offset и способ его определения. Если число
   успешных обновлений подтверждено журналом, укажите `accepted_updates`; иначе
   оставьте `null`. Отсчёт хоста должен быть один для всех интервалов.
3. Обработайте файл:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\energy_analysis.py --cfn .\runs\energy-020\recording.cfn --windows .\runs\energy-020\windows.json --output .\runs\energy-020-analysis
```

Программа интегрирует U×I с линейной интерполяцией записанной мощности, отдельно
считает полную энергию и энергию после вычитания среднего фона. Для заданного
диапазона смещения находятся минимум и максимум интеграла, включая внутренние
экстремумы, а не только два крайних сдвига. Это **анализ чувствительности записи**,
не доверительный интервал точности прибора. Отрицательный результат после
вычитания фона сохраняется и не заменяется нулём.

NRG пересчитывается из заявленных Wh в J без эмпирического множителя; расхождение
с интегралом U×I остаётся в отчёте. Предыдущее расхождение примерно в четыре раза
автоматически не исправляется. До прояснения единиц/часов, независимой проверки
времени и точности приборного тракта результаты обозначаются как пилотные.

Деление энергии длинного блока на число принятых обновлений даёт среднюю энергию
обновления **вместе с транспортом и ожиданиями этого протокола**. Оно не отделяет
энергию flash от USB и работы хоста. Для окончательного сравнения нужно несколько
независимых блоков, одинаковое состояние flash и заранее выбранный порядок.

## 3. Физическое отключение питания — только после подготовки схемы

**С имеющимися только ESP32, Pico 2 и FNB58 этот этап ещё не готов к запуску.**
Нужен внешний high-side/load-switch для 5 V, допускающий управление EN сигналом
3,3 V; конкретную схему надо проверить по документации выбранного устройства.
GPIO15 Pico управляет только входом EN. Он не должен питать ESP32 напрямую.
Общие земли, допустимые токи, подтяжка EN к нулю и защита от обратного питания
проверяются до подключения. У USB-линии данных должен отсутствовать обходной VBUS;
второй USB-кабель или GPIO способны оставить MCU под питанием. Перерезать провод
или соединять неизвестные контакты без проверенной схемы не предлагается.

Подготовлены:

- `tools\pico_power_controller.py` — MicroPython на Pico 2, GPIO15;
- `tools\powercut_runner.py` — Windows-контроллер опыта;
- 200 заранее подписанных LR_B-пакетов с версиями 10001…10200;
- `docs\power_wiring_TEMPLATE.json` — явная запись проверенной схемы.

При запуске скрипта Pico GPIO15 остаётся входом без управления питанием до команды
`ARM PHYSICAL`. Команды `ID`, `ON`, `OFF`, `CUT delay_ms off_ms` возвращают JSON.
Для коротких delay контроллер использует собственный таймер. Это не калиброванный
генератор импульсов: момент внутри операции flash без отдельного измерения неизвестен.

После приобретения и проверки силового ключа:

1. Установите MicroPython и загрузите скрипт как `main.py` на Pico 2 обычным для
   вашей установленной среды способом. Конкретную модель платы/образ следует
   проверить перед прошивкой Pico. ESP32 на этом этапе не перепрошивается скриптом.
2. На ESP32 должна работать новая прошивка completion020, семейство LR, политика
   bundle, storage_layout=2, готовая версия A/B/C из этого комплекта. Старый 019
   не подходит. Сначала завершите обязательные программные серии основного плана.
3. Закройте Thonny/терминалы, занимающие COM Pico; определите отдельный COM Pico.
4. Заполните `power_wiring_TEMPLATE.json` на основании реальной проверенной схемы.
   Шаблон с `null` не принимается.
5. Только после этого:

```powershell
.\.venv\Scripts\python.exe .\completion020\tools\powercut_runner.py --mcu-port COM13 --controller-port COM_ПОРТ_PICO --wiring .\power_wiring.json --output .\runs\physical-cuts-020
```

`COM_ПОРТ_PICO` заменяется фактическим портом. Программа сначала проверяет идентичность
контроллера и прошивки, выполняет OFF/ON-контроль: при выключении ESP32 не должна
отвечать, а после включения должна восстановить прежний подписанный конвейер.
Отсутствие ответа необходимо, но само по себе не доказывает нулевое питание;
подтверждение отсутствия обходного питания должно быть в описании схемы.

Затем выполняются 200 испытаний: seed 24092026, задержка контроллера 0…80 мс,
выключение на 2000 мс. После каждого проверяются готовность, версия, хеш и один
численный контроль. Результат — прежний или новый конвейер; все сбои сохраняются.
Случайная задержка после команды хоста не означает равномерное распределение по
стадиям flash. Отключение может произойти до передачи или после завершения обновления;
это явно отмечено в журнале и требует классификации при анализе. Для публикации
про фазу стирания нужны внешние маркеры/измерения момента отключения.

Скрипт не восстанавливает прошивку, не повторяет автоматически оборванное обновление
и останавливается при неожиданном состоянии. После ошибки сохраняйте каталог,
не запускайте заново ту же серию и не стирайте плату до анализа. После этой ветви
версии будут ≥10001; обычные A/B/C уже не могут быть установлены без отдельного
задокументированного лабораторного сброса. Это ещё одна причина выполнять её последней.

Физический скрипт и MicroPython-контроллер здесь **не испытаны на оборудовании**.
Проверены ограничения протокола и расчётные части на ПК; надёжность отключений
потребует первого пробного подключения с реальным внешним ключом.
