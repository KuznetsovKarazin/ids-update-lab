# Независимая проверка хранения 020

**Итог: PASS в явно заданной модели прерывания NOR-операции.** Контрпример
прежней схемы воспроизведён. В новой схеме повреждение старого неактивного слота
не помешало загрузке принятой B. Аппаратных отключений питания здесь не было.

## Что проверено непосредственно

Скомпилировано фактическое C++-ядро 020 с `-Wall -Wextra -Wpedantic -Werror`.
Зафиксированные исходники и их SHA-256 указаны в `REVIEW_METADATA.json`.

- **354 759 проверяемых условий**, **22 283 моделируемых прерывания**.
- После моделируемых прерываний и отказов чтения успешно выполнены **22 319
  последующих обновлений** с повторной загрузкой. Это не статистика физических
  устройств и не число независимых лабораторных испытаний.
- Прерванные записи: все битовые префиксы каждого вызова записи модели,
  метки слота, тела selector и его метки активации.
- Прерванные стирания: все байтовые префиксы первых 4096 байт, дополнительные
  границы и полное стирание. Для каждого вызова записи/стирания дополнительно
  160 детерминированных произвольных битовых масок с долями 0,01; 0,1; 0,5; 0,99.
- Два исходных состояния: принятая версия 2 и версия 64. Второе состояние
  заполняет обе страницы; очередная установка стирает старую страницу,
  содержащую ранее корректные записи, при сохранении последней записи на другой.
- Исправная версия после сбоя должна быть старой либо полностью установленной
  новой; до записи метки selector разрешена только старая. Полностью записанная
  последняя метка обязана активировать новую даже при потере ACK.
- После восстановления проверены SHA-256 модели и запрет повтора её версии.
- 70 последовательных прерываний после тела selector исчерпывают доступные
  позиции; последующее завершённое обновление остаётся возможным.
- Ошибка каждого чтения при обычном обновлении, при ротации журнала и при
  загрузке приводит к отказу операции, а не к пропуску недоступной страницы.
- Повреждение выбранного слота и несовпадение его digest с selector приводят
  к fail-closed. Неактивный повреждённый слот не блокирует исправную B.
- Искусственно заданный uint64_max не переполняется; дублирование максимального
  sequence отклоняется. Последовательность не может легально достигнуть этой
  границы при обычных возрастающих uint32-версиях, это защитная проверка.
- Все шесть программных точек прерывания дают предусмотренное состояние.
- Неполная первичная подготовка либо оставляет полностью готовую заводскую
  модель, либо требует явной повторной подготовки (`unprovisioned_dirty_store`).
- Для одного логического байта исчерпывающе проверены все 256 значений и все
  256 подмножеств изменяемых битов при программировании и стирании. Допустимое
  dual-rail слово не превращается в другое допустимое слово. Это проверка кода
  представления; она не заменяет верификацию всех состояний контроллера flash.

Для большой матрицы используется проверяющий объект, принимающий тестовые
подписи, и настоящий SHA-256 OpenSSL. Таким образом, матрица проверяет порядок
операций и восстановление, **не** криптографическую стойкость. Модельные пакеты
содержат синтаксически корректную LR с двумя признаками и возрастающей версией.

Отдельный опыт `real_signed_counterexample.json` использует настоящие
подписанные A/B из 018, восемь признаков и штатную проверку RSA-2048 OpenSSL:

1. Установлена B; A остаётся в неактивном слоте.
2. В старой A изменён только один бит 0→1 по смещению 24. Метка commit и
   прочие области сохранены.
3. Код 018 выдаёт `committed_slot_invalid`; IDS не готова.
4. Код 020 загружает B, версия 2, с прежним digest.

## Почему порядок операций соответствует цели

Последний допустимый selector остаётся в области, которую обновление не
стирает. Кандидат записывается в другой модельный слот; commit этого слота ещё
не активирует модель. Затем записывается selector, связывающий слот, версию и
подписанный digest. При ротации стирается страница без последнего selector.
Прерванные записи не дописываются и не смешиваются: для следующей попытки
используется полностью стёртая позиция.

Повреждённые записи старой стираемой страницы либо сохраняют прежнее значение,
либо перестают декодироваться. В рассматриваемой модели изменения 0→1 не могут
превратить их sequence в другой допустимый sequence. Именно это свойство
нужно: обычный CRC без дополнительного доказательства такой гарантии не даёт.

## Точные границы результата

Модель предполагает единственную прерванную операцию в правильно адресованной
области: программирование меняет произвольное подмножество требуемых битов
1→0, стирание — произвольное подмножество 0→1. Остальные области сохраняются;
успешное чтение возвращает реальные стабильные байты. Повторные прерывания
между перезагрузками допустимы, но одновременные повреждения других областей
не моделируются.

**Отдельно продемонстрировано ограничение:** независимое повреждение уже
принятого последнего selector может сделать его недопустимым. Тогда старая
допустимая запись может выбрать старую модель. В `real_signed_counterexample.json`
такой искусственный случай действительно загрузил A версии 1 после B версии 2.
Это повреждение находящейся вне текущей операции области, то есть вне заявленной
модели. Следовательно, формулировка «откат невозможен при любых повреждениях
flash» неверна. Произвольная деградация памяти, злоумышленник с записью raw flash,
подмена runtime/ключа и аппаратная anti-rollback защита здесь не закрыты.

Физический обрыв питания может иметь особенности, не охваченные моделью;
испытания на конкретной плате требуются отдельно. Программный `ARM_FAIL` делает
перезапуск между операциями и тоже не заменяет прерывание flash-операции питанием.
Первичная подготовка не обязана самостоятельно восстанавливаться из грязной
памяти без selector. Успешная подготовка — исходная точка гарантии.

## Воспроизведение

На Linux с C++17 и библиотекой разработки OpenSSL:

```bash
python3 completion020/validation/storage_review/run_review.py
```

Если текущий каталог уже `completion020`, путь начинается с `validation/`.
Сценарий собирает временные исполняемые файлы, выполняет проверки и сохраняет
JSON-результаты в этом каталоге. Исходник прежнего ядра включён в `legacy/`,
поэтому внешний архив 018 для этого сравнения не нужен. Сохранённые native-времена
в ответах протокола служат только журналом опыта; их нельзя выдавать за время ESP32.
